# Governance UI

How the Governed Operations screens are put together: the routes, the layers under them, where each rule lives, and what the screens deliberately do not do yet. The on-chain side — `GovernedExecutor`, `AcmeVault`/`AcmeVaultV2`, `TokenAdmin`, `SaucerSwapAdapter` and the proposal model — is described in `docs/ARCHITECTURE.md`; this document starts where a screen reads from it.

## Routes

| Route                      | What it shows                                                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`                        | The live map: in the rail, the proposals still collecting signatures under "Pending operations" and the settled ones under "Recent", each with its status and approvals; the selected one (`?schedule=`) opens its detail under its card |
| `/governance/[scheduleId]` | One proposal: what it does, the schedule's status, the registry entry behind it, the gas and HBAR the treasury pays, approvals, and Sign / Withdraw / Cancel when they apply |
| `/governance/new`          | Opening a proposal: the operation picker, its form, what the council will see, and the wallet transactions that register and/or schedule it                                  |
| `/settings`                | Settings beside the map: the council from the treasury account's threshold key (Mirror), a composer that schedules a council change (wallet-signed, native), and the registry's roles (relay, read-only) |
| `/api/demo/signers`        | Demo only (development server, testnet): the demo co-signers this server can sign for, and one's `ScheduleSign` on a pending proposal |

The four governance pages share one layout, described under "The live map" below; the treasury figures and the council's threshold sit in its map pane, above every one of them. The header's navigation is Live map (`/`, lit on every `/governance/…` route too) and Settings (`/settings`).

The detail route is keyed by **schedule id**, since a proposal is a schedule the governance account pays for. A registry entry that was registered but never scheduled has no schedule id, and so no page.

## Before setup

A freshly scaffolded app has no `.env.local`, and the governance pages have to render anyway. It does have a deployment — `deployedContracts.ts` is committed with the template's own testnet instance — so while none of the ids `yarn setup` writes is set, `getGovernanceEntityIds()` returns that instance's (`DEMO_INSTANCE` in `config/governanceConfig.ts`, which also stands in for the release topic and the co-signing agent) and the rail opens with `DemoInstanceNotice`, saying so and naming `yarn setup`. Once setup has written its ids the demo is out of the picture; some but not all of them is a setup that stopped halfway, and is reported rather than mixed with the demo's. The governance layout resolves the configuration once for all three routes — `resolveGovernanceConfig(chainId)`, which gathers `getGovernanceEntityIds()`, the network and every `getDeployedContract(chainId, name)` a governance screen reads — and renders `SetupNotice` with the error's message, in place of both panes, if it throws. A page inside the layout reads the result with `useGovernanceConfig()` and has no guard of its own. Each of those throws a message naming the command to run. `getDeployedContract` also throws for an entry without a `hederaContractId`, and returns the id typed as a `string`, so a half-written deployment falls into the same notice rather than travelling on as `undefined`.

The guard asks only for what every screen needs: the ids, the network, `GovernedExecutor` and `AcmeVault`. `AcmeVaultV2`, the implementation a vault upgrade points the proxy at, is looked up by the wizard itself with `findDeployedContract`, which returns null where `getDeployedContract` would throw. Without it the map and the rail render as usual, and the wizard shows the vault upgrade with no form and a notice naming the deploy command, while paying a supplier still works. `TokenAdmin`, which the token form acts through, is looked up the same way (its kind's `resolveTargets`), and missing it has the same effect on that kind.

The network comes from `useTargetNetwork()` through `getHederaNetworkNameFromChainId`, never a literal: a token id from the wrong network's config reads as a balance of 0 rather than an error.

## The live map

`app/(governance)/layout.tsx` renders every governance route, so what sits beside the rail stays mounted while the rail changes route. On a wide screen it is one fold below the header, and the page itself never scrolls:

- **The map pane** (about 60% of the width) never scrolls. It is `LiveMapPane`, which reads one snapshot for all of it and plays what changed (see "Motion" below). From top to bottom: `TreasuryStrip` (the treasury's HBAR, the vault's reserve, the treasury's balance of the governed token under its Mirror symbol, its USDC and the council's threshold; every token amount written with the decimals Mirror reports for that token, "—" when they cannot be read) the caption (`MapCaptionLine`, words in `graph/caption.ts`: "Nothing moves until the 2-of-3 council signs." at rest — the rule is the ledger's, and the demo instance's council, which has seated the co-signing agent, reads "2-of-4" — "Drafting." in the wizard, the selected proposal's title and what its lines mean otherwise; when the previewed operation's route cannot be drawn, or a sequence is playing, it says what a screen with no preview says, never half a path) and the map itself (`GovernanceMap`, with the demo layout provided around the pane by `MapDecoratorProvider`), which fills the rest: its box takes the height left over (`flex-1 min-h-0`) and the SVG scales into it, so the drawing never sets the pane's height.
- **The rail** (40%) scrolls on its own and renders the route's page: the proposal list on `/` (with the selected proposal's detail opened under its card), the detail on `/governance/[scheduleId]`, the wizard on `/governance/new`, Settings on `/settings` (same map beside it; the header's Settings link is lit there and Live map is not, and the rail's "← Map" link goes back to `/`). A page is written as panel content — no page-level width or centring, an `h1` at panel size — and the wizard fills the rail's height, scrolling its middle with its submit button in view.
- **Shared state** comes from `GovernanceProvider`, mounted once by the layout: the resolved configuration, through `useGovernanceConfig()`, and `ProposalWizardProvider`, so the draft being written in the rail is readable beside it and a submission survives the rail changing route. Once submitted, the rail says "Sent with your wallet…" (`RailNotice`), the inbox is read again and `/?schedule=<id>` opens (`useOpenSubmitted`), so the new card is open in the rail and its preview is on the map; the draft is kept until that hand-over finishes and then cleared, so the next proposal starts empty. A layout cannot hand props to its page, which is why both are contexts.
- **On a phone** the map pane and the rail stack, and the page scrolls; nothing scrolls sideways.

The list on `/` splits the inbox with `partitionProposals` (`packages/core/src/governance/proposals.ts`), from the schedule's state alone: an open approval round is pending, and an executed, withdrawn or expired one is settled whatever its outcome.

The header shows how fresh the list is: "Mirror Node · polled Xs ago", from the `dataUpdatedAt` of the inbox query. `useInboxUpdatedAt` reads it from the query cache rather than from `useProposals`, so the header needs no council ids, and `MirrorPollStatus` ticks once a second without re-rendering anything above it. It stays hidden until an inbox has been read in this session.

## Reads and state

Server state lives in React Query and nowhere else. Components never write proposal or signature state themselves; they render what the last read returned.

- **Polling** follows `hooks/mirror/mirrorQuery.ts`: queries poll every 5 s while something is pending and slow down or stop once settled. A schedule that executed is only settled once Mirror has served its outcome (`hasFinalOutcome`), since the row that says whether it succeeded can lag the schedule. The council is cached, since only an executed proposal changes it.
- **After opening a proposal**, `useCreateProposal` and `useCreateNativeProposal` invalidate every inbox on the network in their own `onSuccess`, not in the caller's, so the list refreshes even when the screen that submitted has gone, instead of waiting out the 30 s poll of a settled inbox.
- **When a proposal settles** (leaves pending: executed, withdrawn or expired), `useProposals` and `useProposalLookup` invalidate the treasury figures, the council as well for a council rotation, and the registry entry behind a registry call (read while it was pending, it would otherwise go on saying Pending next to Executed), together, so the screen does not wait out their cache and shows one consistent world. The work is `useRefreshOnSettle`: it compares each read with the previous one, so the first read only seeds it, and like `refresh()` below it reads once now and once more a poll interval later.
- **Executed is not succeeded.** Mirror marks a schedule executed whether its transaction succeeded or reverted, so `Proposal.execution` reads the scheduled transaction's own row (`fetchScheduleExecution`): `succeeded`, `failed` with the network's response code, `unconfirmed` until Mirror has it, or `notRun`. The inbox reuses an outcome it already resolved instead of reading it on every poll, and reads the registry entry behind every registry call to its executor, whatever the schedule's state: behind a failed execution, since the revert left it as it was; behind a withdrawn or expired schedule, since ending a proposal for good is withdrawing its schedule and *then* cancelling its entry, so the schedule says "Withdrawn" whatever came after and only the entry can say "Cancelled"; and behind one that ran, since the entry is what says which operation ran — a settled card is titled by it ("Upgrade the vault to v2") rather than by the id it ran. An entry already read as cancelled or executed is carried from the previous read rather than asked again, since the contract never moves one back, so a settled proposal costs one relay read, ever; a pending one is read on every poll, since it can still be cancelled or scheduled again — and so is one the relay still reports pending right after its schedule ran, until the relay catches up. `useProposalLookup` reads one entry for one page the same way.
- **The map animates reads, not clicks.** `useMapSnapshot` composes the inbox, the council and the treasury figures — the same queries the rest of the screen runs — plus two reads that are never polled and are re-read when a registry call settles, the vault's implementation and the governed token (the query the treasury strip shares), into one `GovernanceSnapshot`, and `diffSnapshots` (`services/liveMap/events/mapEvents.ts`) turns two consecutive snapshots into events: `proposed`, `approved` per member (both councils for a rotation), `executed` / `reverted` once `Proposal.execution` has the outcome (never on `executed_timestamp` alone, so a success is never taken back), and `councilChanged`, a threshold change included. The first snapshot only seeds; a proposal that leaves the inbox window, or reappears because its proposer can be read again, produces nothing; and an event whose consensus timestamp is more than `EVENT_FRESHNESS_MS` (a minute) older than the read is dropped, so a tab that was hidden shows the end state instead of replaying it. A signature from another device is an event like any other. Events are deduped by `animationEventKey` (`kind:scheduleId:memberKey`), since an effect can see them twice under `StrictMode`.
- **After a write**, `useProposalLookup().refresh()` invalidates the schedule and the registry entry immediately and again a poll interval later, because Mirror and the JSON-RPC relay both lag consensus by seconds. The delayed read is cleared if the page unmounts first.
- **A signature is confirmed on Mirror.** Sign (the wallet's, `useSignProposal`) and "Sign as …" (`useDemoSign`) wait for the `ScheduleSign`'s own Mirror row (`waitForTransactionRow`, as Withdraw waits for its delete), since a wallet answers before consensus. A row whose result is not `SUCCESS` fails with `ScheduleSignRefusedError` naming it — `SCHEDULE_ALREADY_EXECUTED` when another member's signature ran the proposal first, `NO_NEW_VALID_SIGNATURES` when this key had signed already — and a row Mirror never lists within the retry window fails naming the transaction, so Sign can be pressed again. On `SUCCESS` both re-read the inbox at once (`confirmSignature`) instead of waiting for the next poll, so the map plays the signature as soon as Mirror can serve it.
- **The inbox can be partial.** `unreachableProposers` names proposers whose schedules could not be read (Mirror failed, or the address resolves to no account); the home page says the list may be incomplete whenever it is non-empty.
- **A proposal outside the inbox** — older than `PROPOSALS_PER_PROPOSER`, or a native proposal opened by an account without `PROPOSER_ROLE` — is read directly by `useProposalLookup`, which returns the same `Proposal` shape and refuses a schedule the governance account does not pay for, so a crafted link never reaches a Sign button.
- **Relay reads** go through `createRelayClient` (`packages/core/src/relayClient.ts`), with one retry: the polling already asks again.
- **Amounts from a contract stay `bigint`** until they are rendered, e.g. `formatTinybars(reserve)` (`utils/scaffold-hbar/hbarAmount.ts`).

## What a proposal offers

The rules live in `services/governance/proposalActions.ts` and are tested there; the page only calls them.

- **Open** (`canOpenProposal`): any connected account for a native kind; a contract-backed kind only for a `PROPOSER_ROLE` holder, since `createProposal` reverts for anyone else after charging the fee.
- **Sign** (`canBeSigned`): the schedule is pending, and either it is a native kind with no registry entry, or it is a registry call whose entry was read, is still pending and decodes to one of this template's operations, or one the relay simply could not be asked about (`unreachable`) — the button is still offered there, next to a warning (`UNREACHABLE_REGISTRY_SIGN_WARNING`) that the check could not be made, since the network is the final word either way. A missing or cancelled entry, or one this template does not recognise, still gets no button. Because `unreachable` still offers Sign, the inbox must not make it common: a cold load asks about every registry call it lists, and a public relay answers a burst of reads with 429s, so `fetchRegistryEntries` reads `REGISTRY_READS_AT_ONCE` (4) at a time.
- **Withdraw** (`canBeWithdrawnBy`): the schedule is pending and the connected account created it. The proposer's key is the schedule's admin key, so a `ScheduleDelete` from anyone else is refused by the network; the button is not shown to them, nor with no wallet connected, nor for a schedule created without an admin key (outside this app), which nobody can delete (`SCHEDULE_IS_IMMUTABLE`). That last rule also keeps Cancel's two-step path away from such a schedule: HashPack returns before consensus, so a delete refused there would not stop the cancel after it. A wallet known to refuse `ScheduleDelete` (`signsScheduleDelete` in `services/web3/walletCapabilities.ts`: HashPack today) is never sent the delete: pressing Withdraw opens `WalletLimitDialog` instead of the wallet prompt, since the refusal would arrive looking like a person pressing Reject. The dialog names a wallet that can sign it and offers "Use another wallet", which disconnects this one and opens the wallet chooser (`WALLET_LIMIT_COPY`).
- **Cancel** (`cancelPlanOf`, plus `canCancelRegistryEntry`): offered while the registry entry is pending, as one guided action whose steps depend on the schedule. Once no live schedule points at the entry any more (withdrawn, expired, or ran and failed — `cancellableRegistryId`), it is `cancel(id)` alone, for anyone the contract accepts. While the viewed schedule is still live, it is two transactions in a fixed order, both spelled out in an inline confirmation before anything is sent: delete the schedule, then `cancel(id)` — a live schedule on a cancelled entry can still reach its threshold, revert with `ProposalNotPending` and bill the governance account for the gas. Only the schedule's creator can delete it (their key is its admin key), so that path is the proposer's; an account that may cancel but did not create the schedule is told Cancel comes once the round is over. `useCancelProposalFlow` runs the two steps, not the component: it reads whether this browser already deleted the schedule from the mutation cache (`WITHDRAW_PROPOSAL_MUTATION_KEY`) rather than from its own state, because Mirror keeps reporting a deleted schedule as live for a few seconds and the card holding the panel remounts once it catches up — so if the delete went through and the cancel failed or was rejected, the card says the schedule is withdrawn but the entry is not cancelled yet, and the retry sends the cancel alone, never a second delete. A delete counts as done only once it is confirmed: the wallet answers before consensus, and a `ScheduleDelete` can still be refused there — a proposer key rotated since the schedule was created (`INVALID_SIGNATURE`), or the last signature landing first (`SCHEDULE_ALREADY_EXECUTED`). So `useWithdrawProposal` waits for the delete's Mirror row and succeeds only on `SUCCESS` or `SCHEDULE_ALREADY_DELETED`. Any other result is a `ScheduleDeleteRefusedError`, and the flow stops before asking for the cancel, with the schedule still live. While it waits the card says so (`confirmingWithdraw`, "confirming the delete on the network…"). The standalone Withdraw goes through the same confirmation. Anyone can open another schedule of `execute(id)` for the same entry, so the viewed one is not always the only one: `otherOpenScheduleOf` looks through the inbox (the query the map already polls) for another pending schedule of the same entry, and while one exists Cancel is replaced by a note linking to it. That check only sees what the inbox lists — a schedule opened by an account outside the proposer list is not there. `canCancelRegistryEntry` decides *who* may press it: `GovernedExecutor.cancel` is open to the entry's own `proposer` and to any `EXECUTOR_ROLE` holder — in this template, only ever the governance account — read from `RegistryEntry.proposer`, the contract's own ground truth, and never inferred from the schedule's creator (the two coincide in this app's own flow, but nothing guarantees that in general). Addresses are compared case-insensitively against Mirror's `evm_address` for the connected account and for the governance account (`useAccount`, read only while the entry is pending). Once the round is over, someone the contract would refuse sees the reason instead of a disabled button; while it is live, the Cancel card is not shown to them at all. Withdraw stays its own card beside Cancel: it ends one round, Cancel the proposal. The same dialog opens in place of Cancel's confirmation when it deletes first, and not on the cancel alone, a contract call every wallet signs.

Wallet rejections are shown as `WALLET_REJECTED_MESSAGE` (`services/web3/hederaSigner.ts`, next to `isWalletRejection`) rather than as a failure. A transaction the node refused as `TRANSACTION_EXPIRED` — the approval came after its valid duration, about two minutes from when it was built — becomes a `TransactionExpiredError` carrying that duration (`isTransactionExpired` reads both the SDK's precheck message and a wallet's HIP-820 `{ code: 9000, data }`), and `MutationError` says it expired, that this transaction was not sent, and to try again within the window. The network only answers that once the wallet submits, so a request left sitting in HashPack would keep a screen waiting for ever: `useExecuteBeforeDeadline` (`hooks/useWalletRequest.ts`), which every governance write goes through — open, Sign, Withdraw, Cancel — stops waiting at the transaction's own deadline (its valid start plus its valid duration, both fixed in the body the wallet signs; the test signer answers at once and is left to the SDK's own regenerate-and-retry) with a `WalletRequestExpiredError`, worded as "reject it in your wallet, then try again". A late approval is refused by the network, since the wallet cannot change the body it signs; only a local clock ahead of the network's can end the wait early, so a success that arrives afterwards is kept rather than dropped: every query is refreshed, a late registration is kept as the unscheduled entry (the retry only schedules it), a late schedule clears it, and the wizard names the transaction.

### The proposal list on `/`

`app/(governance)/page.tsx` splits the inbox with `partitionProposals` and renders each proposal as an `OperationCard`: the kind's icon and title (`proposalIdentityOf` — the registry entry's operation once it was read, "Run entry N of the registry…" before, or, for a body the decoder did not recognise, the reason, as a warning), its family ("contract · via registry" / "native · no registry"), three stage dots (Create · Sign · Executed, read out as a sentence), how many signatures it still needs or, once settled, how it ended — with "entry cancelled" when the registry entry was cancelled under it, so a withdrawn-then-cancelled proposal reads "Withdrawn · entry cancelled" — and while pending a time-left chip (`expiryCountdown`) that turns amber and pulses in the final hour, then a chevron. While the inbox loads, card-shaped placeholders stand where the cards will be. The heading carries the pending count as a pill (read out as "N pending"), with the rail's one note under it — "Each one runs by itself the moment the 2-of-3 council has signed it. There is no execute button." (`runsByItselfNote`, the live rule once the council is read) — and settled proposals follow under "Recent", a heading of the same size. A card lifts its border and darkens under the pointer; it offers no link of its own, since the chevron already says it opens in place, and `PendingOperationsList` shows the first `COLLAPSED_VISIBLE_COUNT` with a "Show N more" toggle (`foldedList` / `expandedList`), opening the list on its own when the selection sits past the fold; "Show fewer" folds it back from there too, until the selection moves. The selection lives in the `schedule` query param (`useSelectedSchedule`), replaced rather than pushed and without scrolling, so a reload or a shared link reopens the same card. `ScheduleSearch` finds a proposal by schedule id through `useProposalLookup`, the same read the detail uses, which is how a proposal outside the inbox (see "A proposal outside the inbox") is reached from `/`.

### The proposal detail rail

`components/governance/rail/ProposalDetailPanel.tsx` is the presentational body of a proposal's detail; `ProposalDetail` owns the reads (`useProposalLookup`, `useHederaSigner`) and hands it the resolved `Proposal`. The route `/governance/[scheduleId]` mounts `ProposalDetail` as the whole rail, under a "← Map" link back to `/` with that proposal's card open. On `/`, the card the URL selects (`?schedule=`, `useSelectedSchedule`) opens the same `ProposalDetail` underneath it as the `inline` variant (`variant="inline"`: one heading level down so the page's outline stays whole, a title smaller than the page's own, the narrower padding a phone-width card can afford, and each fact's value under its label rather than in a column beside it); pressing the open card again closes it — the card's button is a disclosure (`aria-expanded`, and `aria-controls` naming the region that holds the detail while it is open) — and the first pending proposal is pre-selected once per visit, on the first inbox read, so closing it does not reopen it and a proposal that turns up after a first read with none pending does not open by itself. A schedule the inbox does not list — found by the search or named by a link — shows as the search's result instead, with the field filled in with its id and its detail under that card, which opens and closes like any other: it stays beside the field that explains why it is on screen and never among the inbox's own sections, even when it has settled. The result sits in the search landmark but outside its form, since the detail's own buttons would otherwise submit the search. When the open card changes place — a Withdraw moves it from pending to settled on the next inbox read — it stays open there, and `useRefocusMovedCard` puts focus back on its button in the new place and scrolls only as far as it takes to show it; it does so only when focus had fallen to the page, so a viewer who moved on elsewhere is left there. The panel itself reads `useCouncil` (sharing the cache `useProposalLookup` already populated with the same arguments) to label approvers, and owns the Sign mutation; `WithdrawCancelActions` owns Withdraw and Cancel. While the proposal is read, `ProposalDetail` shows a placeholder in the panel's own shape rather than a spinner.

From top to bottom the panel shows: on the page, the schedule id, the kind's title and the card's line; under a card only a screen-reader title, since the card right above shows it. Then the family, what the operation does (`describeRegistryOperation` / `describeScheduledOperation`) and the path it travels as chips (`routeNamesOf` over the map's own graph, so "Treasury → Proposal registry → Vault" reads exactly as the map labels those nodes, and nothing is shown for a route the map cannot draw); Create → Sign → Executed (`ProposalStages`); the large "N more signatures needed · 2-of-3 council · k signed" line with the time left — the approvals, said once; "Confirming on the network" while a signature is on its way or the map still plays the proposal; the result once it ran — for a council rotation, titled by what it made: "The co-signing agent is seated · 2-of-4 council" when the agent's key is in the new council and was not in the one before (the council before is read from the Mirror Node's account history at the execution time, `useCouncilBefore` → `fetchCouncilKeyBefore`, once, in `hooks/useRotationResultTitle.ts`; the rule is `rail/rotationResult.ts`), "The council is now 3-of-4" otherwise or when that read fails, and "Executed" while it is read; the council seat by seat; how a pending proposal ends ("There is no reject button…", with its expiry) — once, and not the map's status note again, which already sits above the map; HashScan (`HashScanLinks`: the schedule, the transaction that created it and, once it ran, the scheduled transaction, on the network's own explorer from the chain config, `getHashScanUrl`); what a proposal that did not run left behind; Withdraw and Cancel; and, folded under one disclosure, the raw ids, the function, the gas limit and the scheduled body.

The names come from the map: `ProposalDetail` reads `useLatestComposedMap` — the map as composed for this deployment by `useComposedMap`, the one composition path the map pane uses too, from the latest read of the queries the map already keeps, with the host's layout from `MapDecoratorProvider` — and hands the panel `memberNamesOf` and `routeNamesOf`, so "Alice" on the map is "Alice" in the council rows. Without the demo layout both fall back to the generic names.

- **`ApproverList` / `CouncilMemberRow`**: one row per council seat, named as the map names its node (`memberNamesOf`; `memberLabel` for a seat the map does not show), with the map's caption as a badge ("demo co-signer"), the account under the name, "your wallet" on the connected account's own seat, and whether it has signed ("Signed", "Not yet", or "Didn't sign" once the round is over). When the app is given the co-signing agent's account (`NEXT_PUBLIC_CO_SIGNING_AGENT_ACCOUNT_ID`, read by `useCoSigningAgent`), the seat its key holds is named "Co-signing agent" with an "AG" avatar, and carries the map's caption for it ("seated by the council" on the demo map) wherever the map names that seat the agent too; while it holds none, the single council's list ends with a dashed "Co-signing agent · not a member · not seated" row saying "Approve “Add the co-signing agent” to seat it (2-of-4 council)." — the wizard's proposal that seats it, and the council that would make, from the live one (threshold unchanged). Without the variable there is no agent row. Sign sits on the viewer's own row only, and names the signer it will ask: the connected wallet by the name its WalletConnect session reports ("Sign with HashPack", "Sign with Kabila"; "Sign with your wallet" when it reports none, `signLabel`), or the test signer. A connected account the proposer list does not know may still hold a seat the app cannot match, so it gets the button under the list instead; a known proposer without a seat gets none. The proposer's own signature counts when they hold a seat (`countThresholdSignatures`), so a freshly opened proposal reads "1 signed". A council rotation renders two lists — "Current council" against `proposal.progress` and "Incoming council" against `proposal.incomingProgress` and the operation's own `council` — each heading with its own count, since the schedule waits for both thresholds. Other parts of the screen can add to a seat that is not the viewer's through `seatExtras` (a badge in place of the map's caption — the demo's "demo key", tinted like "your wallet" but softer — an action in place of the status, shown only while that seat has not signed): the demo co-signers use it (see "Demo co-signers").
- **Relay lag on Cancel**: the JSON-RPC relay reads a block or two behind, and a signer returns once the transaction is submitted — HashPack without a receipt — so neither an immediate re-read nor the submission settles it. `useProposalLookup` exposes `markRegistryEntryCancelled()`, called by `useCancelProposalFlow` once the cancel is sent instead of `refresh()`: the entry reads "cancelled" straight away, and the registry query polls until the relay agrees. A "pending" answer inside `CANCEL_CONFIRMATION_WINDOW_MS` is taken for lag and does not flash the entry back (which would offer Cancel again, a second transaction that reverts); still "pending" after it, the cancel did not take and the entry reads pending again. The cancel is recorded in the query cache (`hooks/mirror/sentCancels.ts`) rather than inside the hook, so the inbox reads it too: `useProposals` applies it through `select`, on the way out of the cache and never into it — the inbox keeps an entry it once read as cancelled for good (`previous`), which would outlive a cancel that did not take — and the card on `/` reads Cancelled together with the panel under it. When the wait ends either way, the inbox is re-read. `refresh()` (after Sign or Withdraw) re-reads the inbox along with the proposal for the same reason.
- **Cancel or let it lapse**: a registry entry has no expiry of its own; only its schedule has. An entry left alone after its schedule was withdrawn or expired stays pending and nothing runs, but anyone can schedule it again for the council to approve — the panel says so once the round is over. Cancel is what ends it for good: while the round is live it deletes the schedule first so the proposal cannot revert later at the treasury's cost; once it is over it needs no schedule and no signatures.

## What a proposal says

The screen that asks for a signature is the one that has to explain the mechanism, so the domain values never reach it as they are. `proposalLabels.ts` turns them into words:

- the proposal's status (`proposalStatusLabel`): "Collecting signatures", "Executed", "Failed when it ran", "Executed, confirming the result" while Mirror has not served the outcome, "Withdrawn", "Expired";
- for a failed execution (`executionFailureLabel`), the network's response code and what retrying takes: for a registry call whose entry is still pending, scheduling `execute(id)` again for the council to sign — not proposing it again; for a native kind, scheduling the same operation again;
- the registry entry: its state when it was read, "None: the network runs this operation directly" for a native kind, "No usable entry: do not sign" when the registry has none or the call names another contract, "Could not be read right now" when the relay did not answer;
- approvals as "n of m required signatures" (`requiredSignaturesLabel`), counted against the threshold rather than the council's size (a 2-of-3 council with both signatures in reads "2 of 2 required signatures") — for a council rotation one count for the current council and one for the incoming council, since the schedule waits for both thresholds (see "A rotation collects signatures from two councils" in `docs/ARCHITECTURE.md`);
- the council's rule (`councilRuleLabel`, "2-of-3"), shared by the map, the treasury strip and the wizard;
- the inbox's headings on `/`: "Pending operations", "Recent" and "No proposal is waiting for signatures." (`INBOX_COPY`), and the note under the heading (`runsByItselfNote`).

The wizard's words across kinds — each kind's title and hint, the path chips it travels, the gas and expiry rows, who approves, and the one-or-two-transactions CTA — live in `components/governance/wizard/copy.ts`, a kind's own form words in its folder under `wizard/kinds/`, the map's — node names and captions, edge captions, the legend and the inspector — in `components/governance/graph/copy.ts` (the line over the map in `graph/caption.ts`, the previewed operation's words in `services/liveMap/preview/kinds/`), and the rail's — the card's family and status line, the detail's steps, signature line, notes, HashScan labels and the Withdraw / Cancel cards and confirmation — in `components/governance/rail/copy.ts`, so each module holds one screen's words.

A pending proposal also says that it runs as soon as the threshold is reached and that it expires, with nothing run, if the threshold is not reached by its expiration time.

## Opening a proposal

`useCreateProposal` sends two transactions: `createProposal` registers the call in `GovernedExecutor`, then a `ScheduleCreate` wraps `execute(id)` for the council to sign, with the proposer's key as admin key. The registry id only comes back through Mirror (`proposalIdFromContractResult`), so the hook waits for indexing with backoff (`waitForMirrorIndexing`). Once `createProposal` has gone through, a failure of anything after it — Mirror not yet indexing the registration, the wallet rejecting the `ScheduleCreate`, the network refusing it — leaves the entry registered and unscheduled, and the hook keeps it (`unscheduledEntry`, `services/governance/unscheduledEntry.ts`). Submitting the same call again (same executor, target and calldata, `isEntryFor`) reads the entry's id if it was not known yet and only schedules it, so a retry never registers a duplicate; the wizard's button then reads "Schedule entry N with your wallet" and says why. A registration that reverted left no entry and is forgotten; once the `ScheduleCreate` has gone through the entry is forgotten too, since a second schedule on it would revert and bill the treasury once the first one ran. The entry is held in memory only: after a reload a retry registers again, and an entry left unscheduled stays pending until its proposer cancels it. `useCreateNativeProposal` schedules a transfer or a council rotation directly, with no registry entry. Both send their transactions through `useWalletRequest`, which holds the step the wallet is being asked for (`walletRequest`: register or schedule, step n of m, and the transaction's valid duration from the SDK) until it answers; the wizard shows it in place of the footer note — "Step 1 of 2: register the call in the registry. Approve it in your wallet — the request is valid for about 2 minutes." — so a submit waiting on the wallet says where to act. A retry that only schedules a kept entry is one step, and the test signer is not asked to approve anything. Past the transaction's deadline the step stops waiting (see the expired approvals above) and the button can be pressed again.

Both hooks take an already-encoded proposal from `@sh/core/governance/encode`, which enforces the chain invariants (positive amounts, a reachable threshold, no duplicate council key) before anything becomes a transaction.

The wizard is two components so that it can live in a page or in a side panel. `ProposalWizardProvider` owns the chosen kind, the current draft, its preview and the submit mutation, and reports the new schedule id through `onSubmitted`; `ProposalWizard` renders the picker, the form, the preview and the submit footer, with no route, title or setup guard of its own. The host renders those, gives the wizard a height (it fills it, scrolls its middle and keeps the footer in view) and the level of its headings. Because the submission lives in the provider, closing a panel while the wallet signs does not lose it, and anything else inside the provider — a map drawing the draft — reads the same preview through `useProposalWizard()`. On the live map the host is split: the governance layout runs the setup guard and mounts the provider (`GovernanceProvider`), whose `onSubmitted` opens the proposal on `/` (`GOVERNANCE_ROUTES.selected`), and `/governance/new` adds only a title and the way back to the map.

The wizard knows no kind by name. Each kind is a folder under `components/governance/wizard/kinds/` — its form, its copy and a `kind.ts` that pairs the form with `resolveTargets`, which finds the contracts and ids the kind acts on from the resolved config, or returns the notice saying why it cannot be proposed on this network (the contract it acts through is not deployed) — and `kinds/registry.ts` lists them, one line each, in a record keyed by the kinds in `kinds/wizardKinds.ts`. `defineWizardKind` keeps each kind's own targets type inside its entry, so the wizard renders whichever kind is picked with the same call and shows its notice in place of the form. Offering a new kind here is its folder, a draft module and one line in each of those two lists; the whole recipe, from `@sh/core` to the co-signing agent, is [How to add a proposal kind](../AGENTS.md#how-to-add-a-proposal-kind) in `AGENTS.md`.

The picker is native radio buttons sharing one name across its two groups ("Contract calls · through the registry", "Native · no contract, no registry entry"), so a keyboard moves the choice with the arrow keys. It is disabled while a submission is pending, since picking another kind resets the draft. The wizard says why the button is disabled rather than leaving it greyed out: no wallet connected, a vault upgrade with no `AcmeVaultV2` deployed to point the proxy at, the proposer list still loading or unreadable, an account without `PROPOSER_ROLE` for a contract-backed kind, a recipient or holder that is malformed, still being looked up, or not an account, a holder that never associated the token it would freeze, or a recipient that could not hold the token it would be sent. The words live in `components/governance/wizard/copy.ts`, the wizard's own copy module, and in the copy of the kind that raises them.

`/governance/new` builds a draft from the form through `services/governance/drafts/`, whose module for the kind converts amounts without rounding and calls the encoders, and previews it through `decodeScheduledOperation` / `decodeRegistryOperation`: what the proposer reviews is what the detail page will show the council. A body the decoder cannot fully read cannot be submitted. The vault upgrade always runs `initV2(limit)` in the approved call, since `initV2` is a reinitializer anyone could call afterwards. Under its implementation address the upgrade form says whether a published release vouches for it, read the way the co-signing agent reads it (`assertReleaseTopicIsSigned`, then `checkImplementationAgainstManifest` in `@sh/core`, through `useReleaseCheck`): a topic without a submit key, or a deleted one, whose releases are unsigned claims and are not read at all (the agent refuses to start on it); the release whose code hash matches the deployed code, no release naming the address, a release naming it whose hash no longer matches, a topic that could not be read, or an implementation whose code could not be read (`ReleaseReadError` says which of the two reads failed, most likely Mirror not yet indexing a contract deployed moments ago) — with a HashScan link to the topic. It is information only and never holds the draft back; the agent is what refuses. The line is hidden when `NEXT_PUBLIC_RELEASE_TOPIC_ID` is not set (`getReleaseTopicId`). `decodeRegistryOperation` reads the limit back out of that call, so the preview and the detail page both name it; an upgrade that runs any other initializer decodes as unrecognised and is offered no Sign. The schedule's memo is the kind's title.

The token form acts on the token whose pause and freeze keys `TokenAdmin` holds (`NEXT_PUBLIC_DEMO_TOKEN_ID`), shown read-only with whether it is paused right now (`useToken`). A freeze or an unfreeze names one holder, typed as an id or an EVM address and resolved through the Mirror Node like a transfer's recipient (`accountLookup`); the form then reads the holder's relationship with the token (`useTokenRelationship`). An empty answer is not a failed read but an account that never associated the token, which the network would refuse to freeze (`TOKEN_NOT_ASSOCIATED_TO_ACCOUNT`) after the governance account paid for the call, so the form says so and offers no draft. A token without the key the operation needs is refused the same way: a `pause_status` of `NOT_APPLICABLE` means no pause key, and a holder's `freeze_status` of `NOT_APPLICABLE` means no freeze key. `TokenAdmin` could only revert with `TOKEN_HAS_NO_PAUSE_KEY` / `TOKEN_HAS_NO_FREEZE_KEY` after the council had approved it. A pause is drafted only once the token has been read, and a token that cannot be read blocks it. The draft names the token and the holder by their long-zero addresses (`longZeroAddress`), which the token system contract resolves like any other form of the same account.

The transfer form pays out HBAR or one of the tokens the treasury holds — the setup's token and the DEX configuration's USDC — as a native `CryptoTransfer`. A token amount is converted with the token's decimals from `useToken` (`parseTokenDecimals`), never assumed, and refused rather than rounded when it is finer than they allow. Before drafting a token payment the form reads the recipient's relationship with the token: an account that never associated it and has no automatic association slots (`max_automatic_token_associations` of 0) would make the network refuse the transfer once the council approved it, so the form says so and offers no draft; one with slots is told the transfer associates it, provided a slot is still free when the threshold is reached.

The wizard's one council rotation seats the co-signing agent. Its form asks for one account, the agent's, and reads it through `useAccount`: the draft keeps every current member in the council's order (each seat read back into a key with `memberPublicKey`), adds the agent's key last and leaves the threshold as it is, so a 2-of-3 council becomes 2-of-4 — `draftCouncilRotation` with those members, no encoder of its own. The account is refused, with the reason, when it is not an account, holds no single key (`singlePublicKey`), holds a key other than ECDSA (the agent in `packages/agent` signs with an ECDSA key), or already holds a seat (`memberKeyOfAccount` against the council's keys) — entering Bob says he is a member already; the agent's own account, which `yarn setup` creates outside the council, is the one it seats. The form names the council it would make with the map's names for the seats (`memberNamesOf` over `useLatestComposedMap`, as the rail's detail does: the demo decorator `MapDecoratorProvider` gives the map, the account ids without it, "your wallet" for the seat the map calls "You"), states that it takes two thresholds — the current council's and the proposed one's own, the schedule waiting until both are met (see "A rotation collects signatures from two councils" in `docs/ARCHITECTURE.md`) — and that the co-signing agent never signs a rotation, so both have to come from human members. Every number is the ledger's, and so is the picker's hint (`→ 2-of-4 council`, from the kind's `hint`). The field starts with the configured agent account (`NEXT_PUBLIC_CO_SIGNING_AGENT_ACCOUNT_ID`, else the demo instance's, through `getCoSigningAgentAccountId`), passed as `suggestedAgentAccountId` in the kind's targets, and stays editable; it starts empty when none is configured. Once that account is seated, as on the demo instance, the prefilled field is refused with words of its own — the configured agent already holds a seat, so there is nothing left to seat — rather than the member refusal that asks for another account. The preview's "Function" row reads the proposed rule off the decoded key, and "Who approves" names both councils, the proposed one as the decoder read it back. A general editor for adding and removing members is not part of the wizard; Settings composes general council changes (see "Settings"). The schedule's memo for any rotation is "Change the council", and the rail titles a rotation by the council it proposes ("Change to a 2-of-4 council"); the picker keeps "Add the co-signing agent" for the wizard's kind.

## Settings

`/settings` shows who governs, from the two layers that answer it. **The council** is the treasury account's threshold key read from the Mirror Node (`useCouncil`), one row per seat named as the map names it (`councilSeatOf`, shared with the rail's `ApproverList`) with no signature column; the co-signing agent's seat is named as the agent when the council holds its key, with the map's caption ("seated by the council" on the demo map), and an agent the app is told about (`NEXT_PUBLIC_CO_SIGNING_AGENT_ACCOUNT_ID`) that holds no seat gets a dashed "not a member" row saying which council ticking it would propose — or, when its account holds a key the agent could not sign with, why it cannot be seated. The page checks the agent once (`useUnseatedAgent`) and hands the same answer to the card and the composer. **The composer** proposes a new council: every seat as a checkbox (the unseated agent too, when its account holds a single ECDSA key — `agentSeatOf`), "Signatures required" with − and + kept within the ticked seats, and "Accounts to add" for an account that holds no seat yet, typed as an id or an EVM address and read through `useAccounts` (`memberAccounts.ts` turns each one into the seat its own single key makes; a key list, a threshold key or a seat already offered is refused with the reason). It warns about a 1-of-n or n-of-n council, about the viewer leaving — the viewer's seat is read from the connected account's own key (`useAccount`), so it warns a council member who is not a proposer too, and says they keep `PROPOSER_ROLE` only when they hold it — and about a current council that cannot reach its threshold without the agent's seat (`currentCouncilNeedsAgent`: no change could run, yet it does not block, since it is the council the ledger already has) (warnings only; the encoder is what refuses — no members, a repeated key, an unreachable threshold), refuses to schedule a council whose other seats cannot reach the threshold without the co-signing agent (`councilBlockOf`: the agent never signs a rotation, so such a change could never run), shows "What the council will see", and says that the schedule waits for both councils' thresholds and that a co-signing agent never signs a rotation. Its note reads "One transaction. The map shows the council this would create in dashed violet." It builds the same rotation draft as the wizard (`draftCouncilChange` → `draftCouncilRotation`) and puts it in the layout's one draft (`ProposalWizardProvider.setDraft`), so it is submitted through the same path and footer (`ProposalSubmitFooter`: one native schedule, "Schedule with your wallet"); leaving the page empties the draft. On this route the map caption reads "Council settings. The council lives in the treasury account’s key, not in any contract." and, while a change is composed, "Dashed violet is the council this change would create: a 2-of-4 council." with every seat of that council joined to the treasury by a dashed violet line (the `councilSettings` preview target). It is offered to any connected account (`canOpenProposal`: a native proposal needs no role). **The contract roles** are read from the executor over the relay (`useRegistryRoles`, `fetchRegistryRoles` in `packages/core/src/governance/roles.ts`): `PROPOSER_ROLE` holders come from the proposer list `useCouncil` already reads (the one the inbox is built from; a failed council read says the proposers could not be read), `EXECUTOR_ROLE` ("Treasury account … — the only holder" only when that is what was read) and the role admin ("The registry itself" only when every admin holder is this executor) from `roles.ts`, which keeps its own role hashes and member reader beside `council.ts`. There is no form to grant a role: changing who may propose is itself a proposal, and no such kind is offered. The screen never shows `proposalCount`. Its words live in `components/governance/settings/copy.ts`.

## Demo co-signers

**Demo only.** On a proposal's detail, each demo member's row (Alice's, Bob's) carries a "demo key" badge and, while the proposal still waits on that member, "Sign as Alice" / "Sign as Bob"; a note under the council says their keys live server-side, testnet only. The button asks `app/api/demo/signers` (POST), which signs that member's `ScheduleSign` with the key `yarn setup` keeps in the gitignored `setup-state.json`. The demo account pays for its own signature, as a member signing from a wallet would; the operator is not involved. The button reads "Signing as …" until Mirror lists the signature and the inbox has been re-read (see "A signature is confirmed on Mirror"), then stays disabled until the read shows it, and the signature banner does not announce it (`signAs`). The buttons exist only when `GET /api/demo/signers` lists a member: on a deployment where nobody is offered, the rail looks exactly as it does without this feature.

**What the server checks, every time.**

- It signs only on testnet: `HEDERA_NETWORK` must say so (unset counts as another network), and so must the network the app targets.
- Only for a request whose `Host` is `localhost`, `127.0.0.1` or `[::1]`, which stops a page on a rebound domain (DNS rebinding). It is not a network boundary: anyone on the same network can send that header themselves.
- Only under the development server (`NODE_ENV` is `development`; any other build mode, production included, is refused), and there is no opt-in.
- Only for a JSON POST naming a `0.0.x` schedule and a demo member whose key it holds.
- Only for a schedule the governance account pays for, still pending, whose body the decoder understands, whose registry entry (for a call to this executor) is still pending, and which still waits on that member's key on a council it needs (both councils, for a rotation) and that is still short of its threshold, so a member whose council is already met — or a proposal the network has yet to run — is never offered.
- It re-asks `canBeSigned`, and a registry it cannot read is a 502 rather than a warning.
- **Never for the co-signing agent's seat:** a demo member is excluded when its account or its key is the agent's, known from `NEXT_PUBLIC_CO_SIGNING_AGENT_ACCOUNT_ID` (whose key is read from the Mirror Node) and from the agent's own account `yarn setup` records in `setup-state.json` (`demoAccounts.agent`, beside Alice's and Bob's; the server only ever loads the council members' keys, `DEMO_COUNCIL_MEMBERS`, and refuses `agent` as a member). While neither exists, or the configured account cannot be read, it signs for nobody, and GET says why (`unavailableReason`), since the agent could still be sitting on a demo seat.
- Responses carry only public fields and fixed messages.
- `next.config.ts` excludes `./setup-state.json` from the route's traced server output. The exclusion matches a plain file; a `setup-state.json` that is a symlink is traced at its target.

**Why this is acceptable in a demo.** The keys belong to throwaway testnet accounts `yarn setup` created, holding a few HBAR. They are read only on a development server that refuses mainnet and production builds, never leave it, and are never bundled. The route re-checks every rule the page applies and never signs for the co-signing agent, so it cannot bypass the agent's policy. The point is to let one person with one wallet watch a threshold complete. It is not a defence against anyone who can reach that server: `next dev` listens on every interface, so on a shared network (a hackathon's Wi-Fi) whoever can POST JSON to it with `Host: localhost` can have Alice and Bob sign a pending proposal, and two demo keys meet a 2-of-3 threshold on their own. Start it with `yarn next:dev -H localhost` on a network you do not trust.

**What a real project would do.** Every council member signs from their own wallet or custody (HashPack, a hardware wallet, a KMS- or HSM-backed signer); no server holds a member's key, because two server-held keys *are* the threshold. Automated approval is a separate account with its own policy and audit trail, like `packages/agent`. The route and the keys do not exist.

**Removing it** takes two steps: (1) delete `app/api/demo/`, `services/demoSigners/`, `hooks/useDemoSigners.ts` and `components/governance/demo/`; (2) remove the `useDemoSeats` import, its call, the two `seatExtras` props and the note from `rail/ProposalDetailPanel.tsx`, the demo cases and the `useDemoSigners` mock from `ProposalDetailPanel.test.tsx`, and the demo copy pin from `.harness/validators/static.json`. What stays behind is harmless, since nothing sends a `signAs` mutation any more: `ApproverList`'s `seatExtras`; the `signAs` mutation key, `signedAsOf` in `hooks/useRemoteApprovals.ts` and `signedAs` in `SessionWrites` (`services/liveMap/remoteApprovals.ts`), which then only ever read an empty list; the `server-only` dependency and its mock in `vitest.setup.ts`; and the tracing exclusion. They are generic on purpose: the banner's rule (a signature this session asked for on another seat's behalf is its own) does not depend on the demo, and moving it into the demo would make `useRemoteApprovals` import from a folder step 1 deletes.

## The governance map

`components/governance/graph/` draws the graph `services/liveMap/model/graph.ts` derives. `LiveMapPane` only renders what `useLiveMap` returns (the figures, the council, the tokens, the map, its frame, its caption, the inspector and the selection). The hook takes the `GovernanceConfig` the host's setup guard resolved, reads the council, the inbox and the treasury through `useMapSnapshot` (so it adds no polling of its own), plays what changed, announces signatures from elsewhere, and composes the map through `useComposedMap` from the world it holds: that hook builds the configured entities with `governanceEntitiesOf` — the vault, `TokenAdmin` and the swap adapter as targets, the token, the SaucerSwap router as an external contract the adapter has exactly one authority link to, and where the money is (router → treasury, the vault's reserve) — composes the map with `composeMap` and the host's layout (`useMapDecorator`, from `MapDecoratorProvider`). The pane hands it to `GovernanceMap`, which shows it through `GovernanceGraph` (or says it is reading, or that the council could not be read). `GovernanceGraph` only draws.

- **Shapes.** An account is a circle (`AccountNode`), a contract a rounded rectangle (`ContractNode`, dashed when it is outside the system), a token a hexagon (`TokenNode`), and the governance account the one large node (`TreasuryNode`), with the council's rule written inside ("2-of-3") and the approvals of the proposal being shown as a separate `SignatureRing` — violet at rest, amber while a signature arrives, mint once the threshold has run and coral when the run reverted (`MapFrame.ring.tone`).
- **State lines.** The vault's and the token's captions say what state the ledger has them in — "v1 · deposits only" or "v2 · withdrawals on", "Active" or "Paused" (`nodeStateCaptions`, words in `MAP_NODE_STATES`). They are the snapshot's `nodeStates`: the vault proxy's ERC-1967 implementation slot (`useVaultImplementation`) and the token's `pause_status` from the same `useToken` query the treasury strip reads its symbol and decimals from, so the token is read once. Each is read on its own and is null when its read fails, which leaves that caption and nothing else; both are re-read when a registry call settles (`useRefreshOnSettle`) and change on the map with the figures, when the run lands (`nodeStatesShown`), and stay once its lines relax. A vault running code that is neither of the template's two implementations keeps its caption.
- **Edges.** One `GraphEdge` for every phase — `rest`, `preview`, `progress`, `complete`, `failed` — set by the frame the map is given (`MapFrame`); at rest authority is a solid grey line and money a dotted one, and an `intent` edge (what a pending proposal would use) is drawn only while a frame names it, gated by `canShowIntent` rather than `canBeSigned`: a registry call the relay could not read offers Sign but draws no intent, since the app cannot say what the entry currently holds. The `Legend` stays on the canvas. An edge that does not end at the treasury — every `PROPOSER_ROLE` arc from a proposer to the registry — goes around it (`routeOnMap` in `geometry.ts`), on whichever side its straight line passes, so registering never looks like it runs through the council; this holds for any layout, the fallback included.
- **Ids.** Graph ids contain `+/=:.->`, so nothing puts them in a DOM `id` or a selector: an item carries `data-node-id` / `data-edge-id`.
- **Keyboard.** The map is one Tab stop with a roving tabindex: the arrow keys (and Home / End) move through the nodes in reading order, then the edges, and a focus ring shows where. An item is a `button` when the host passes `onActivate`, a `graphics-symbol` otherwise; only a button shows the pointer, over its whole hit area. Every item has an accessible name, and every name is real SVG text.
- **Layout.** Without a decoration every node is placed by role (`autoLayout`) and named by role, by the proposer account holding a seat, or by its id. The co-signing agent's seat (`NEXT_PUBLIC_CO_SIGNING_AGENT_ACCOUNT_ID`, read by `useCoSigningAgent` and handed to `composeMap` with the connected account) is named "Co-signing agent" with an "AG" monogram as soon as a member node carries its key — the council's, or a rotation's that the preview draws — as the rail's council lists name it (`composeMap` does it for every layout; a layout that names the seat otherwise, and "You", keep their name and their first letter); the demo draws the agent as a ghost until then and puts its seat where the ghost was. The seat the connected account holds (`useHederaSigner().accountId`) is named "You" over any other name; the account is matched to a seat through the proposer list, the only accounts whose keys the map reads, so with no wallet, or one that is not a proposer, no seat is. `decorate` is where a demo places and names the nodes, and leaves out the ones its story has no place for (`hidden`: nodes, dropped with their edges, and single edges by id — from what is drawn only): the demo names the seat of `HEDERA_COUNCIL_ACCOUNT_ID` "Council account", hides the seatless proposer `yarn setup` grants the role to so it can open the seed proposal, and hides Alice's and Bob's PROPOSER_ROLE lines to the registry, keeping only the council account's — without the demo all of them are drawn, and the inbox lists every proposer's proposals either way; the colours are daisyUI tokens plus `--color-map-preview` in `styles/globals.css`, so both themes work.
- **Motion.** The map animates reads, never clicks: poll → diff → play. `useProposalAnimationSync` queues the events `useMapSnapshot` reports (deduped by `animationEventKey`, since a read can report one twice) and plays them one at a time through a single timer; while the queue plays, the map and the treasury figures show the world the first event leads from (`held`), and move on only between reads, so a threshold run is never cut short by the next poll and the new state is never drawn before the sequence that leads to it. A rotation's `councilChanged` waits for its own run's outcome before it plays, and until it plays the map keeps the council it replaces (`councilShown`), so the new seats never appear ahead of the run; if Mirror never confirms the outcome, it plays anyway after `MAX_PARKED_READS` reads. If more than `MAX_QUEUED` events wait, the queue gives up replaying and shows where things are now. What plays is data in `services/liveMap/motion/`: `sequenceOf` turns an event into cues with durations (`MOTION_MS`, the timings of the choreography — a proposer's pulse into the registry for a registry call, nothing for a native one; a signature's pulse into the treasury and the ring filling; a threshold run's ring snap, a comet per hop of the proposal's path, the target flashing while the figures count, a hold and a relax; a failure stopping at the hop before its target, turning the path coral, shaking the target and bringing the comet back). Steps overlap where the choreography does — the registry flashes and the ring fills while their pulse is still landing — so a signature and the run it completes play back to back: the run's first comet leaves 1110 ms after the signature's pulse, and the path relaxes 2600 ms after the run arrives. The figures and the vault's and token's state lines move on as the run arrives, or, for a failed run, once its comet is back, to the read the run arrived in (`treasuryShown`, `nodeStatesShown`) — never to a newer one, which later events still waiting do not lead to — and the held world keeps them for the events of the same read that follow, so the figures never count backwards. `frameOf` turns a cue into a `MapFrame` — which edges are lit and how, which comets travel, how full the ring is, which node flashes or shakes. A signature from another device plays exactly like one sent from here: the map only sees reads. Lines never stay lit: every sequence ends at rest.
- **The rail waits for the map.** The layout's `MapPlaybackProvider` (mounted by `GovernanceProvider`) runs `useMapSnapshot` and `useProposalAnimationSync` once, so the map pane (`useLiveMap`) and the rail read one playback. The queue says which proposals it is still playing or has waiting (`busyScheduleIds`, counted from the render that brings their read); the rail shows each of them as the map draws it (`proposalShown`, through `useShownProposals` for the lists and `useShownProposal` for the detail): the card stays in Pending, and the detail keeps its count, its stages and, for a rotation, the council rows the map shows until the run lands, then flips to Executed together with the figures. The detail also holds the map's copy while this session's own signature on it is on its way (`useSignatureInFlight`), since its lookup can read the signature before the inbox does. Meanwhile it says "Confirming on the network" with DaisyUI's moving dots (`ConfirmingLine`; only the words under reduced motion), from the wallet's answer — or the "Sign as …" press — until the run lands; a card the map is playing says it too, whether or not its detail is open. Sign stays disabled meanwhile, since the held copy still shows the signer's seat unsigned. When the queue gives up on a backlog, it names nothing it dropped, so nothing is held or spins forever. Everything else in the rail stays live.
- **The preview says what would happen.** `useMapPreview` (composed by `useLiveMap`, which `LiveMapPane` only renders) reads what the rail shows: the wizard's draft on `/governance/new` — or, until its form holds one, the kind the wizard has picked — or the proposal `/governance/[scheduleId]` or `?schedule=` names, or, on `/settings`, the council change composed there (`previewTargetOf`). The Settings target is its own (`councilSettings`) rather than the wizard's `draft`: it draws only a council rotation, so a draft left by another kind never shows on that route, and it is keyed `councilSettings` so ticking a seat or moving the threshold does not restart the drawing. `previewFrameOf` (`services/liveMap/preview/`) turns it into a frame: its route in the mode's phase, dashed violet while the council could still sign it (`canShowIntent`), mint once it ran and succeeded, muted dashes once its round ended without running, with everything else dimmed to 35% except the council and the treasury. The treasury ring is filled with the approvals and "N more needed" sits under the rule (`NeedCount`), and "executed" or "reverted" replaces it once a run ended, also while a sequence plays. The words for what would change sit on the node it reaches ("would become v2", "would be paused", "would receive 40 ℏ"; `NodeCaption`, also in the Treasury's accessible name). They come from one module per kind in `services/liveMap/preview/kinds/`, listed in `registry.ts`: adding a kind is one module and one line, and TypeScript refuses a kind without words. A body the decoders do not fully understand, and a registry entry that is missing or could not be read, get no preview at all; a previewed proposal that would not run (void) draws its path muted and an empty ring. "would become v2" is said only when the implementation is the release the deployment recorded as next; any other implementation reads "would be upgraded". The drawn graph carries the previewed operation (`GraphSnapshot.previewed`), so a draft's or a settled transfer's recipient has a node to land on; a payment to an account whose key holds a seat — Alice, Bob — lands on that seat, matched through the proposer list, never on a new node. A kind picked before its form holds an operation is previewed as a sketch of its route (`sketchOf`, each kind's `sketch` in its own module): the same dashed violet and dimming, through the contracts the configuration names for it — the vault, the swap adapter back to the treasury, the Token admin and the token, the co-signing agent's seat once its key is read — with only the words that need no form ("would be upgraded", "would sell HBAR", "would receive a payment"). It is keyed like the draft it becomes, so filling the form in crossfades the words instead of redrawing the path. The caption then says "Dashed violet is the way “…” would go. Fill in the form to see exactly what it would do."; a picked kind the map cannot draw yet — a payment on a map with no stand-in for its recipient — says "Fill in the form to see where “…” would go." and "Pick an operation type." is left for when no kind is picked. The path draws itself through a mask whose dash slides along it (600 ms), the dim and the words' crossfade take 320 ms, and all three are instant under reduced motion. While a sequence plays, it owns the map and the preview waits (`paneFrameOf`). Selecting another proposal, or opening the wizard, closes the inspector without moving focus: `useLiveMap`'s `dismiss` effect is keyed on the preview's target. A malformed schedule id in the route reads "not found" (`useProposalLookup` refuses it before asking Mirror).
- **The demo map's council** always shows You, Alice, Bob and the "Co-signing agent". The agent is the account named by `NEXT_PUBLIC_CO_SIGNING_AGENT_ACCOUNT_ID` (`useCoSigningAgent`, whose `seat` is its key), a ghost ("not a member yet") until a rotation proposes or seats that key. `useMapEnvironment` reads it once for both the map and its preview, and `useComposedMap` threads the agent's configured account and its seat (`agentAccountId`, `agentSeat`) into the decorator's `MapContext`, so the decorator reads nothing from the environment. Once a rotation proposes or seats that key, the node is drawn at the ghost's slot, still named "Co-signing agent" with the monogram AG ("You" when the connected account holds it). While proposed it keeps the ghost's faded, dashed look and the caption "not a member yet", with the preview's dashed violet line, and is not lit as one of the council that decides; once the council holds it, it is a solid member captioned "seated by the council", the inspector has words of its own for it, and there is no ghost. Without a configured agent, or before its account is read, the static ghost stays. Bob is always Bob, and a fourth member that is not the agent is laid out by `autoLayout` as before.
- **The demo map's Supplier** is always drawn below the treasury, as an account outside the system (a circle, captioned "outside the system", like the prototype's supplier), with no line to it at rest. The demo asks for it through `MapDecoration.recipientStandIn`, which adds the graph's `RECIPIENT_STAND_IN_NODE_ID`, a node marked `standIn` that names no ledger entity (no id in the inspector, and no ref finds it); a picked "Pay a supplier" reaches it. A payment that names an account the map has no node for — a draft, or a pending or selected proposal — takes the Supplier's place, name and words, with the account id underneath; a payment to an account the map has, such as Alice, is lit on that node and the Supplier stays unlit. The co-signing agent's account is paid under the agent's name, and an account named by an EVM or key alias never takes the Supplier's place, since the map cannot tell whose it is; a picked "Pay a supplier" draws nothing while a pending payment to an outside account holds the Supplier's place. The generic map has no stand-in: a recipient appears only once named.
- **A signature from elsewhere is also announced, and so is a proposal the wallet has sent.** When a read reports an approval this session did not send — a member signing from another device, the co-signing agent, anyone — `LiveMapPane` hands its host a notice naming the seat as the map does and the proposal as the rail does ("Bob signed … from their own device. Nobody on this screen pressed anything — the poll saw it.", `remoteSignatureNotice`, words in `remoteSignatureMessage` in `copy.ts`), and the governance layout shows it as a banner at the top of the rail (`RailNotice`, which also says "Sent with your wallet…" once a proposal is submitted: a polite `role="status"`, dismissible, cleared after 8 s or by the next one). What this session sent is read from its own mutations in the query cache (`useMutationState` on `GOVERNANCE_MUTATION_KEYS`: signing, and opening a proposal, whose creator's approval arrives with it, and asking the server to sign for a demo co-signer (`signAs`, whose variables carry that seat's key, so the approval is this session's for that schedule and that key only, from the moment it is sent)), so nothing keeps state about the ledger; the rule is `remoteApprovals` (`services/liveMap/remoteApprovals.ts`) and the hook `useRemoteApprovals`, which judges each approval once. An approval is this session's only when it is by the connected account's own key (read once from the Mirror Node, `memberKeyOfAccount`) and on a schedule this session signed or opened; until that key is read, every approval on such a schedule counts as its own, so nothing this session may have sent is announced.
- **At rest the map holds still.** Nothing on it loops: no drift, no breathing glow (the glow behind the treasury is a still tint). It moves only when a read reports something (the sequences above) and when someone points or picks: under the pointer or keyboard focus an edge thickens from 1.6 to 2.6 in 180 ms and a node's border brightens; keyboard focus also draws its ring. Nothing is written over the map: what an item means is its accessible name, and the inspector's once it is selected. A layout may name its areas (`MapDecoration.regions`; the demo writes "Council" down the council's column and "Contracts" over theirs).
- **Movement is CSS**, so it stays at 60 fps and reduced motion is honoured live by the stylesheet: a comet is a short head with a faint, wider tail, each a dash of its edge's own path moved by `stroke-dashoffset` (`animate-map-comet`, `-tail`, `-back`), a phase change is a colour transition, the ring fills and snaps, a plate flashes, a failed target shakes (`styles/globals.css`, written to `MOTION_MS`). Animate `transform` on the SVG, never the `translate` property: Chrome repaints the whole drawing every frame for an animated `translate` on SVG (measured: about one frame in eight dropped). Under `prefers-reduced-motion` comets and flashes are not drawn and colours swap at once, while the sequences keep their timing so every state is still shown long enough to read. The one exception is `AnimatedNumber`, which counts the treasury figures in a leaf with `requestAnimationFrame` and shows the new value at once when `usePrefersReducedMotion` says so.
- **The inspector explains what you pick.** A click, or Enter / Space on the focused item, opens one card for a node or an edge (`MapInspector`); picking another replaces it, and its × or Escape anywhere in the pane closes it and gives focus back to the item (`useMapSelection`); selecting a proposal on the rail closes it too, without moving focus. The card has a kicker in the legend's words (`Account`, `Contract · GovernedExecutor`, `Token`, `Who may act`, `Where the money is`) — a seat whose account also holds `PROPOSER_ROLE` reads "Account · may also propose", from the ledger's proposer list, whatever words a layout gives the seat — the node's name or `From → To`, one paragraph, and the ids folded under "Ids and links", each linked to HashScan through the target network's block explorer. `inspectorContentOf` (`graph/inspector.ts`, pure) picks the words: by role and edge kind from `copy.ts` — the treasury's paragraph names the council's rule as the ledger has it — unless the layout has its own for that id (`MapDecoration.inspector`, which the demo writes for its vault, token, Alice, Bob and the supplier). A ghost gets its name and a neutral line. The selected item is `aria-expanded` and `aria-controls` the card, which is also what draws its highlight (`group-aria-expanded:`); the card is a labelled region, not a dialog, so it traps nothing and the arrow keys keep walking the map. On a wide pane it floats over the map's lower left corner; below `sm` it sits under the map, full width, so it never hides the item it explains.
- **Removing the demo layout**: delete `components/governance/graph/demo/`, then, in `app/(governance)/layout.tsx` — the only file that imports it — remove the `decorateDemoMap` import and the `decorate={decorateDemoMap}` prop on `MapDecoratorProvider`. The map falls back to `autoLayout`, and the rail and the wizard to the generic names.
